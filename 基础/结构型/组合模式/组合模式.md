# 组合模式（Composite）深度透析

组合模式解决的核心问题是：如何把“单个对象”和“由对象组成的树”用同一套接口来操作，让调用方不必区分“叶子”和“容器”。

------

## 1. 意图与本质

GoF 定义：将对象组合成树形结构，以表示“部分-整体”层次；让客户端对单个对象和组合对象的使用保持一致。

用一句话说：

> 统一接口 + 递归结构 + 透明或安全地处理叶子/容器

你的 `AuraHUD` 注释里其实已经点到了这个结构：

AuraHUD.hLines 12-16

 \* 要拥有指向用户界面组件的指针

 \* 负责创建用户界面组件

 \* A.HUD是一个Actor，所以它可以放在关卡里，或者被玩家控制器拥有

 \* B.拥有一个大控件

 \* C.这个大控件里有很多小控件

`OverlayWidget` 是大容器，里面的 HealthBar、DamageText 等是小控件——这正是组合模式在游戏 UI 里最常见的形态。

------

## 2. 结构拆解

用于树状类结构，比如UMG下的UI关系

| 角色                  | 职责                                           |
| :-------------------- | :--------------------------------------------- |
| Component（组件接口） | 声明叶子和容器共用的操作                       |
| Leaf（叶子）          | 没有子节点，实现具体行为                       |
| Composite（组合节点） | 持有子节点列表，Operation 往往递归委托给子节点 |
| Client（客户端）      | 只依赖 Component 接口，不关心是叶子还是树      |

------

## 3. 两种实现方式：透明 vs 安全

这是学 Composite 时最容易忽略的分叉。

### 透明组合（Transparent Composite）

- `Add` / `Remove` / `GetChild` 写在 Component 基类里
- 客户端完全统一，叶子也“看起来”能 AddChild
- 缺点：叶子调用 Add 要么无意义，要么要抛异常/空实现

### 安全组合（Safe Composite）

- 管理子节点的接口只放在 Composite 里
- 客户端需要区分类型才能 AddChild
- 缺点：失去部分“完全一致”的透明性，但更类型安全

UE 的 UMG 更接近安全组合：`UWidget` 有通用接口（Render、Visibility），但 `AddChild` 主要在 `UPanelWidget`（容器）上，普通 `UTextBlock` 不能加子节点。

## 5. 游戏开发中的典型应用场景

### ① UI 层级（最常见）

OverlayWidget (Panel)

├── HealthBar (Panel)

│   ├── ProgressBar (Leaf)

│   └── Text (Leaf)

├── ManaBar (Panel)

└── DamageTextContainer (Panel)

​    └── WBP_DamageText (Leaf)

操作如“隐藏所有 HUD”“整体淡入淡出”“统一 Scale”，都应对 Root 做一次，而不逐个找子控件。

### ② 场景/Actor 附着层级

AActor (Composite)

├── MeshComponent (Leaf)

├── HealthBar WidgetComponent (Leaf)

└── WeaponSocket

​    └── WeaponActor (Composite)

`GetAttachedActors()`、递归销毁、递归设置 Collision 都是组合思想。

### ③ 行为树 / 技能节点树

Selector (Composite)

├── Sequence (Composite)

│   ├── CheckRange (Leaf)

│   └── Attack (Leaf)

└── Flee (Leaf)

`Execute()` 在 Composite 上递归，Leaf 上执行具体逻辑。这是 AI 领域最标准的 Composite。

### ④ 菜单 / 选项树

设置界面、天赋树、背包分类，都是“节点可嵌套节点”。

## 6. 与相关模式的边界

| 对比                    | Composite                        | 区别                                      |
| :---------------------- | :------------------------------- | :---------------------------------------- |
| Decorator               | 动态叠加职责，通常单层包装链     | Composite 是树形 ownership，父子同构      |
| Chain of Responsibility | 请求沿链传递，通常只有一个处理者 | Composite 是对所有子节点都执行            |
| Flyweight               | 共享内部状态                     | Composite 关注结构统一，可配合使用        |
| Iterator                | 如何遍历                         | Composite 定义结构，Iterator 定义遍历方式 |

记忆口诀：

- Composite：整棵树一起处理
- Decorator：一层包一层增强
- Chain：沿链找第一个能处理的

------

## 7. 优点与代价

### 优点

1. 客户端简单：只面向 Component 接口
2. 易扩展新节点类型：新增 Leaf/Composite 子类即可
3. 天然支持递归算法：渲染、更新、统计、导出
4. 符合开闭原则：新增节点类型不必改现有客户端

### 代价

1. 类型约束变弱：透明组合下，叶子也可能被误 AddChild
2. 共享父节点困难：一个对象通常只能属于一个 Composite（UI 里 Reparent 要谨慎）
3. 顺序/生命周期复杂：子树销毁顺序、Tick 顺序、ZOrder 都要额外设计
4. 过度统一接口：Leaf 被迫实现无意义的 Add/Remove

## 8. 在 Unreal Engine 中的“原生 Composite”

你不需要从零实现，引擎大量 API 已是组合模式：

| 系统          | Component 接口    | Composite                  | Leaf                   |
| :------------ | :---------------- | :------------------------- | :--------------------- |
| UMG           | `UWidget`         | `UPanelWidget`             | `UTextBlock`, `UImage` |
| Actor         | `UActorComponent` | `AActor`（通过 Attach）    | `UStaticMeshComponent` |
| Slate         | `SWidget`         | `SOverlay`, `SVerticalBox` | `STextBlock`           |
| Behavior Tree | `BTNode`          | `BTCompositeNode`          | `BTTaskNode`           |

你在 Aura 里的层次：

AAuraHUD

  └── OverlayWidget (UAuraUserWidget → UUserWidget)

​        └── [蓝图子控件树]

AAuraCharacter

  └── HealthBar (UWidgetComponent → 内部又是一棵 Widget 树)

  └── DamageText (UDamageTextWidgetComponent)

`InitOverlay` 创建根 Widget 并 `AddToViewport()`，之后引擎对 Viewport 里的 Widget 树做递归渲染与布局——这就是 Composite 在运行时的工作方式。

## 9. 设计时该怎么用（实战 checklist）

设计一个“可能是树”的系统时，问自己：

1. 是否存在 part-whole 层次？（有 → 考虑 Composite）
2. 客户端是否应统一处理单个与组合？（是 → 强烈适合）
3. Operation 是否应递归传播？（Render、Update、Save、Enable）
4. 叶子能否有子节点？（不能 → 倾向 Safe Composite）
5. 是否需要遍历所有节点？（需要 → 可再加 Iterator 或 Visitor）

### 一个简化的 C++ 游戏向骨架（Safe Composite）

*// 组件接口 — 所有节点都能执行*

```c++
class IUIComponent

{

public:

​    virtual ~IUIComponent() = default;

​    virtual void Draw() = 0;

​    virtual void SetAlpha(float Alpha) = 0;

};

*// 叶子*

class UTextUI : public IUIComponent

{

public:

​    void Draw() override { */\* Draw text \*/* }

​    void SetAlpha(float Alpha) override { Opacity = Alpha; }

};

*// 容器*

class UPanelUI : public IUIComponent

{

​    TArray<TSharedPtr<IUIComponent>> Children;

public:

​    void Add(const TSharedPtr<IUIComponent>& Child) { Children.Add(Child); }

​    void Draw() override

​    {

​        for (auto& Child : Children) Child->Draw();

​    }

​    void SetAlpha(float Alpha) override

​    {

​        for (auto& Child : Children) Child->SetAlpha(Alpha);

​    }

};

客户端：

void ShowHUD(TSharedPtr<IUIComponent> Root)

{

​    Root->SetAlpha(1.f);

​    Root->Draw();

}
```

## 10. 常见反模式（游戏项目里很常踩）

| 反模式                               | 问题                   | 更好做法                       |
| :----------------------------------- | :--------------------- | :----------------------------- |
| 手动维护扁平 List，绕过树结构        | 增删子节点时容易漏更新 | 让 Composite 自己管理 Children |
| 到处 `Cast` 到具体 Panel 再 AddChild | 客户端与具体类型耦合   | 依赖接口，或 Factory 创建子树  |
| 叶子实现空的 AddChild                | 透明组合的滥用         | 改用 Safe Composite            |
| 在 Leaf 里硬编码找父节点             | 破坏封装               | 事件向上冒泡，或 Mediator      |
| 一棵 UI 树跨多个系统各自持有子指针   | 双重所有权、悬空指针   | 单一 Composite 拥有子节点      |

------

## 11. 小结

Composite 不是“把对象放进数组”那么简单，而是：

1. 用统一接口表达树形结构
2. 让容器的行为通过递归委托给子节点
3. 让客户端不用关心“这是按钮还是面板”

在游戏里，UI、场景层级、行为树、技能节点、关卡对象组，几乎都是 Composite。你在 Aura 里写的 HUD/Widget 体系，已经在使用这个模式，只是引擎帮你封装好了 `UWidget` / `UPanelWidget` 这层抽象。

# 组合模式的作用（简要）

组合模式用来处理「部分–整体」的树形结构，让单个对象和由对象组成的容器对外用同一套接口操作。

## 核心作用

1. 统一操作
   客户端不必区分「叶子」和「容器」。例如对根 UI 调用一次 `Hide()`，整棵子树都会隐藏。
2. 简化客户端代码
   不用写大量 `if (是Panel) { 遍历子节点 } else { 直接处理 }`，多态和递归由组合节点自己完成。
3. 灵活扩展结构
   新增一种控件或节点类型，只要实现同一接口，就能挂到树上，不必改现有调用代码。

## 一句话

> 把「单个」和「一组」当成同一种东西来用，让树形结构更好写、更好扩展。

## 游戏里的典型例子

- UI：Panel 里套 Button、Text，统一渲染、显示/隐藏
- 场景：Actor 附着子 Actor/Component，统一销毁或更新
- 行为树：Selector/Sequence 下挂具体 Task，统一执行流程

本质就是：用树组织对象，用统一接口管理整棵树。
